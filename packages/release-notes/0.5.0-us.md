## What's new in 0.5.0

Smaller tools that each do one thing, `systemctl isolate` that follows the
unit files, and systemd's console settings for the text-console gettys.

- **A sixth package, `uinitconverter-devices`:** the units that devices
  want are started by `initconvert-devices`, a tool of its own that reads
  udev and asks the daemon; the daemon no longer watches udev. `dnf upgrade
  ./*.rpm` installs it with the others (`uinitconverter` requires it).
- **`initconvertd` is only the daemon:** a reload runs `initconvert-gen` as
  a program instead of a copy of it inside the daemon;
  `initconvertd start|stop|restart` are removed (use `systemctl` or
  `s6-rc`), and `initconvertd log` is now `initconvert log`.
- **No shell at a service's start:** the generated `run`, `finish` and
  logger scripts are execline, and the start limit
  (`StartLimitBurst=`/`StartLimitIntervalSec=`) counts s6-supervise's death
  tally.
- **`systemctl isolate`** refuses a target without `AllowIsolate=yes` and
  keeps running units with `IgnoreOnIsolate=yes`.
- **Text-console gettys** (getty@, serial-getty@, console-getty,
  container-getty@, kmsconvt@) get `TTYReset=`, `TTYVTDisallocate=` and
  utmp/wtmp records from the runner, so `last` shows getty logouts. Checked
  on real hardware with getty@tty8. kmscon's logins run on a pts and get no
  logout record, as on systemd.
- **Fixes:** a `DefaultDependencies=no` unit could start before `/run` was
  labelled at boot (sm-notify's SELinux denial): `mount-api` now comes up
  first, in a change of its own. A reload no longer fails when s6-rc's lock
  is busy. A start right after a reload no longer hangs for its start
  timeout; `initconvert-linkwatch` 0.3.0 also resends a lost start.

After upgrading, run `sudo initconvert init --yes` and reboot, as in the
README's "Update"; the `mount-api` order and the devices service apply from
that boot. Standalone tools: `uinitconverter-linkwatch` 0.3.0, the others stay
at 0.2.0.

**Known issues:**
- After a reload that was held back, a unit that only the new database has
  can't be started until the next boot, and every later reload is held back
  too. The start's error says so.
- Reloads that apply live may log `s6-supervise: fatal: unable to chdir to
  NAME` for services they restart or remove, and s6 2.15.1.1's s6-ftrigrd
  sometimes crashes during the update; gen relinks the services and
  retries. When it crashes, a few running services can be stopped or
  restarted before gen relinks them: in the test VM, on the first live
  reload after updating from 0.4.0 (before the reboot), `systemd-hostnamed`
  restarted and `systemd-localed` stopped; both start again on demand over
  D-Bus. Both are upstream behaviour; the system keeps running.
